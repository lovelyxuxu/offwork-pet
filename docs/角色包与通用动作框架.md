# 角色包与通用动作框架

更新：2026-10-21。

状态：已按本设计实现第一版角色包框架（`v0.5.0-preview.1`），使用方式及当前边界见 [角色包制作与使用](角色包制作与使用.md)。`v0.6.0-preview.2` 已提供基础可视化制作界面，见 [桌面生活与互动](桌面生活与互动.md)。在线工坊和部分扩展能力仍属后续范围；本文保留设计目标与迁移依据。

本次补充：按“类似创意工坊，应用提供系统，角色内容由角色包提供”的目标整理平台边界、创作流程和迁移步骤。下文新增的技术拆分与配套格式草案是建议实现方案，不代表这些细节已经实现或逐项确认。

## 平台定位：系统、角色包与工坊

产品定位是可安装角色内容的桌面运行平台。主程序不是预先写好几只宠物再让用户选择，而是读取角色包的声明，运行该角色自己的内容。

可以分成三个部分，按顺序建设：

1. **运行系统**：安装和管理角色包，播放素材，识别输入，执行规则，提供窗口、倒计时和联网等系统能力。
2. **角色内容**：创作者提供外观、动作、交互区域、行为规则、菜单、台词、声音和作者信息。普通用户导入一个文件即可使用。
3. **内容工坊**：以后用于发布、预览、搜索、下载和更新角色包。工坊分发的仍是同一种角色包；没有联网或没有工坊账号，也应能导入和运行本地包。

“像创意工坊”首先意味着内容可独立制作、分享和安装，不要求第一阶段就建设在线商城、账号、审核、评论和自动更新服务。

系统统一的是**能力和格式**，而不是角色的行为内容。例如系统支持区域点击、连续抚摸和动画播放，包决定被操作的位置、播放的动作和结束后的反应。若一个包需要实时 3D 等新能力，必须明确要求相应的框架扩展，不能只靠新增配置获得。

### 普通用户与创作者的使用方式

- 普通用户：在“角色管理”里选择一个包导入，看到缩略图、作者、版本和包提供的互动说明，随后使用、切换、更新或删除。
- 创作者：准备图片、GIF、动画帧或图集，设计动作与交互，在制作工具里预览并校验，最后导出一个包。制作工具是独立的一步，不要求普通用户理解 JSON、帧率或目录结构。
- AI 辅助创作：依据参考图/GIF制作新动作，再整理成同一种标准包；不为每个 AI 工具另建一种运行机制。
- 在线工坊：提供角色包的分发入口，不成为动画执行器；下载和本地导入走同一套校验与安装流程。

角色包格式与制作工具相互配合。第一阶段可先提供模板、命令行校验和预览，再提供可视化制作界面；不能承诺导入任意图片就自动得到完整角色。

## 已确认的目标与边界

- 系统提供通用运行框架，每个角色使用独立角色包，用户可以导入、切换和删除。
- 角色包自行定义动作、素材和触发规则。不同角色的动作种类、数量、名称、帧数和时长可以完全不同。
- 主程序不能把“待机、摸头、捏脸、轻捶”等角色动作写成固定清单，也不能要求所有角色实现同一套动作。
- 新增角色和普通动画动作，通过导入角色包完成，无需修改主程序或重新发布整个应用。
- 用户操作保持简单：选择角色包导入，程序自动管理资源；无需用户手动解压或维护素材目录。
- 已获准开发角色包框架；本次实现本地运行、包管理和 v2 双人互动协议，线上部署另行进行。

此前讨论过只分发一个 exe，随后用户转向独立角色包方案；不能把“所有角色必须塞进一个 exe”继续当成约束。用户仍希望减少无用的外置文件和操作步骤，角色资源由程序管理。

## 框架与角色包的分工

| 框架提供的基础能力 | 角色包定义的内容 |
| --- | --- |
| 资源读取、动画播放、声音播放、缓存管理 | 图片、动画、声音、缩略图及其使用方式 |
| 点击、拖动、悬停、计时、远程消息等事件 | 哪些事件与条件触发哪些动作 |
| 状态切换、动作调度、循环、排队、打断 | 动作之间的关系、优先级、结束后去向 |
| 根据声明生成菜单和操作入口 | 展示哪些动作、显示名称、排序 |
| 连接、能力同步、消息传递和结果反馈 | 支持哪些远程互动及其对应的本地行为 |

框架可以定义通用事件和播放指令，但不能把角色动作的名称或含义写进框架逻辑。例如，框架识别“单击事件”，角色包决定单击后是伸懒腰、变形、发声，还是不响应。

桌面窗口移动、设置、倒计时、联网开关等系统功能仍由框架管理；角色包声明动画行为时不能破坏这些基础操作。

## 动作与状态完全由包定义

- 动作标识属于角色包，可使用任意符合格式的稳定标识，名称用于显示，二者分开。
- 初始状态由角色包指定，不强制存在名为 `idle` 或“待机”的动作。
- 每个动作声明素材、播放速度、是否循环等信息；每个状态或规则声明触发条件、目标动作和后续状态。
- 有限动作结束后，按照包内声明返回某个状态、转入另一个动作或结束本次播放。
- 角色包决定哪些动作允许用户从菜单主动触发，内部过渡动作不必出现在菜单中。
- 支持动作增加或减少，不能使用主程序里的固定枚举决定一个角色是否完整。
- 缺失素材、引用不存在的状态等属于包错误，应在导入时指出。运行期间遇到异常，按照包声明的恢复规则处理；无法恢复时给出反馈并停止该角色播放，不能猜测某个固定“待机”动作必然存在。

行为示例仅用于说明，不是框架内置动作：

| 包 | 包内规则示例 |
| --- | --- |
| 猫咪 | 从“趴着”开始；点击后“伸懒腰”；结束回到“趴着”；长时间无操作后“睡觉”；菜单提供“打滚” |
| 机器人 | 从“巡逻”开始；点击后“变形”；定时进入“充电”；菜单提供“灯光秀” |

两个包可以没有任何相同的动作标识。新增“跳舞”这样的动画，只要使用框架已经支持的播放和规则能力，就不需要改主程序。

如果新增行为需要框架尚不具备的能力，例如新的渲染方式或完整的饱食度系统，需要扩展框架。可配置动作不等于角色包可以自动实现任意新功能。

## 角色包需要描述的信息

设计至少需要覆盖以下信息。建议的文件组织和字段示例见 [角色包格式与运行规则草案](角色包格式与运行规则草案.md)，该草案用于下一步实现评审，不是已经实现的格式规范：

- 包标识、包版本、角色名称、缩略图，以及框架格式版本和所需能力。
- 画布尺寸、绘制区域、定位点及交互区域。
- 资源清单及对应的图片、动画、声音。
- 动作清单及各自动画、帧率、循环等播放参数。
- 初始状态、事件与条件、状态切换、结束去向、异常恢复规则。
- 动作的打断、排队和优先级规则。
- 用户可见的菜单操作。
- 可接收的远程互动及其本地行为映射。

建议第一阶段采用“素材 + 声明式规则”，使用事件、条件、计时器、随机选择和状态切换组合行为。第一阶段不靠导入任意 Python 或其他可执行脚本实现动作；具体规则语法在实现前确定。

## 通用运行模型

框架应提供以下可组合的层次，避免在主程序里继续增加角色分支：

| 层次 | 含义 | 举例（仅属于某个包） |
| --- | --- | --- |
| 素材/动画 | 要显示的连续画面与播放时间 | 一组眨眼帧、一段摆手动画 |
| 动作 | 一次可以被调度的表演，含打断、排队和结束规则 | “开心蹭手”“橘子舞” |
| 状态 | 角色持续处于的情境，含基础画面和可用规则 | “趴在垫子上”“睡着了” |
| 区域 | 角色画布中可响应输入的位置 | 包内名为 `crown` 的头顶区域 |
| 规则 | 什么事件在什么条件下触发动作或切换状态 | 点击 `crown` 后执行“开心蹭手” |
| 对外入口 | 哪些能力可以从菜单或搭子端主动发起 | 菜单“跳舞”、远程“摸摸头” |

这些名称和标识由包自行定义。一个包可以只有一张静态图、一个初始状态和零个互动，也可以有多种状态和许多动作；不能把“必须有几个动作”当作安装条件。

### 输入识别与角色反应分开

- 框架产生统一的单击、双击、按住、移动、进入/离开、拖动开始/结束、连续抚摸、定时和远程互动等事件。具体支持项由能力版本声明。
- “连续抚摸”应是通用的轨迹识别能力，区域由包声明；框架不内置名为“头”的部位，也不内置“摸头后一定开心”。
- 画布坐标、缩放、翻转、窗口移动和命中区域使用同一套变换。第一阶段可使用固定区域，姿态差异明显时按状态/动画覆盖区域；逐帧区域可后续扩展。
- 左键按下先进入候选手势，达到拖动条件后取消单击候选；长按、抚摸与拖动需要明确仲裁。不能同一次拖动又触发点击和摸头。
- 第一阶段可约定：普通左键拖动移动窗口，按住系统修饰键后在角色区域内移动用于抚摸；具体按键由系统设置管理。创作者不能任意抢占系统手势。普通点击仍可由包定义反应。
- 右键系统菜单、托盘退出、恢复位置、暂停和设置属于稳定的系统入口。包提供的动作作为菜单里的独立分组，不替换这些入口。

### 动作调度与运行边界

- 第一阶段只有一个主动作播放通道。状态提供基础表现，临时动作完成后按声明返回状态；多层动作混合不是第一阶段的必需能力。
- 动作声明包内优先级、是否可打断、忙碌时排队/替换/拒绝、冷却和结束去向。相同事件多条规则命中时有固定的选取顺序，不因文件遍历顺序而随机执行。
- 不可打断只约束角色动作之间的替换，不能阻止系统暂停、拖动、切换角色或退出。
- 系统为队列数量、事件频率、规则执行次数和连续切换次数设上限，避免规则自触发后卡住主线程。
- 循环动作若作为临时动作，必须声明退出条件或最大时长，不能永久堵住队列。
- 以实际经过时间计算播放进度，不假定所有包共用当前 20 Hz 绘制时钟。卡顿后允许跳到应显示的帧，不能让队列无限追赶过去的帧。
- 关闭互动、暂停或隐藏时，由框架暂停相应事件和任务；用户的总开关、静音和联网限制优先于包内规则。

## 素材制作与外部格式适配

框架负责播放已有素材。新增“跳舞”不改主程序的前提，是包已经包含相应动画，且行为使用框架支持的能力。

第一阶段建议原生支持静态图、PNG/WebP 序列帧和带显式帧位置/时长的图集。GIF 可先由制作工具转换为标准帧并保留时序；视频、骨骼动画、Live2D 或实时 3D 在需要时作为新的渲染能力扩展，不在第一版同时实现。

Codex Pets 等外部格式通过转换器生成本项目的标准包：

- 把图集行和有效帧转换为显式动画清单，不要求所有行都存在；转头帧可以映射为包声明的方向响应。
- 转换器可以认识外部格式的固定行定义，核心运行时只认识转换后的动画与规则，不能让外部格式的固定动作枚举重新进入主程序。
- 转换不自动补出源素材没有的动作。只有眨眼帧不能据此宣称已经支持自然蹭手或完整跳舞。
- 包保留原作者、素材来源、授权和修改说明；程序代码许可证与角色素材许可证分开记录。

## 双人互动使用动态能力

产品统一使用内置搭子服务 `http://106.54.27.8`，普通用户不填写或选择服务器地址。联网开关、邀请和配对操作仍由用户控制；角色包不能指定自己的中继服务。客户端构造参数可为开发者的本机联调注入测试地址，不作为用户配置保存或展示。

接收方当前角色包声明可接收哪些互动；发送方根据对方声明生成互动入口。框架不固定提供“捏脸、轻捶”按钮。

1. 接收方加载角色后，同步当前角色包的标识、版本和可接收互动清单。
2. 清单中的互动标识、显示名称和接收后的行为由角色包定义。菜单展示信息与本地行为规则分开，远端只需要必要的能力描述。
3. 发送方选择对方支持的互动，通过通用消息发送目标互动标识及必要参数。
4. 接收方使用自己的角色包解析该互动并调度动作，无需发送方安装相同角色包或素材。
5. 切换、删除角色或更新角色包后，重新同步能力。能力变化后收到的旧请求，要重新检查并明确反馈不支持或已失效，不能映射到名称相似的其他动作。

互动标识的作用域和能力版本需要在协议中明确，避免两个角色使用同名动作却含义不同。若发送方还希望播放本机发起动画，只能使用自己包中明确声明的规则；不能要求双方存在同名的发送和接收动作。

建议能力快照同时包含包标识、包版本、内容摘要和本次加载的能力修订标识。即使切回同一个包，也生成新的加载修订；请求绑定其看到的快照，避免旧请求误作用于重新加载的角色。

远端只获得可展示的互动标识、名称、必要参数及限制，不获得本地资源路径、内部动作或整套规则。第一阶段只需提供无参数互动按钮；以后有需要再增加受限的参数类型，不能把任意脚本或表达式通过消息传入。

消息的“请求编号”和“互动标识”是不同字段。收到、进入播放队列、开始播放和播放完成也是不同结果；第一阶段可以只回执“已接收/已排队/拒绝”，界面不得把它说成“对方已经看完”。如果排队后切换角色或过期，必须终结该请求并清理队列。

服务端提供通用转发和校验，不继续依赖固定动作枚举。身份、配对、暂停、隐藏、限频、消息有效期、去重和回执等既有约束仍然适用。角色包不能绕过框架限制。

## 导入、切换和删除

- 导入：用户选择一个角色包文件，程序验证格式、兼容性、资源和规则引用，自动安装到应用管理的角色目录。
- 导入失败：给出具体原因，不留下半安装角色，不影响正在使用的角色。
- 切换：停止旧角色动作、计时器和待播队列，释放其资源引用与缓存，再启用新角色的初始状态和事件规则。
- 删除：角色素材和缓存一起清理。删除当前角色时切换到其他可用角色；没有任何角色时显示导入入口。
- 每个角色都允许删除，不要求保留某个不能删除的内置角色。
- 包文件校验、解包路径约束和资源上限由框架统一执行；具体实现和数值待定。

更新按“新版本先完整验证和准备，成功后替换”的方式进行。相同包标识的不同内容不能直接覆盖正在读取的文件；安装目录按版本与内容摘要隔离，角色选择仍引用稳定包标识。更新当前角色失败时保留旧版本并恢复可用状态。

导入不是“选择后立刻执行”：先在暂存目录检查清单、相对路径、文件类型、解包后大小、图片解码预算、动画引用及规则，再登记为已安装角色。失败只清理本次暂存内容。

当前角色损坏或用户删除最后一个角色时，显示系统的“导入角色/管理角色”入口；这个空状态是框架界面，不是一个不能删除的默认角色。

## 内存与磁盘管理

角色包解决独立分发和磁盘资源管理；避免内存随角色数量膨胀，需要框架同时做到：

- 未使用的角色只读取必要的名称、缩略图等信息，不预加载全部动画。
- 当前角色的素材按需读取，缓存按解码后的实际资源大小设定预算，不能仅按帧数限制。
- 切换或删除时停止旧角色的所有任务并释放相关资源，避免旧对象和缓存持续持有动画。
- 对单张图片尺寸、解码大小、包大小和队列设置合理上限，防止单个角色占用失控；具体数值待测试确定。
- 角色列表缩略图等辅助资源也需要独立且有限的缓存，不能随着打开列表无限累积。

- 缓存键包含包的内容摘要、素材路径和必要的解码规格，防止不同包或更新前后的同名帧串用。
- 用每次角色加载的运行实例标识隔离异步任务。旧实例的图片读取、计时器、声音或远程回调即使晚到，也不能继续操作新角色。

目标是动画内存主要由当前角色和框架缓存预算决定。角色增加会增加磁盘及少量元信息占用，不承诺进程内存完全不变，也不承诺释放后系统显示值立即回落。

## 当前代码与后续迁移范围

本节保留 2026-10-21 实现前的代码快照；下列绑定现已从产品运行链路移除，旧绘制文件只作为初始素材转换参考保留：

- 噜噜使用 `offwork_pet/assets/lulu3d/manifest.json` 和 PNG 动画帧，但路径与动作使用方式仍绑定在现有代码中。
- 噜妹由 Python / Qt 绘制，尚不是独立素材角色包。
- `offwork_pet/sprites.py` 按需读取动画图片，当前最多缓存 64 帧；还不是按实际资源大小控制的通用缓存。
- 角色枚举、配置校验、设置界面、绘制入口、远程动作与服务端校验需要一起梳理，不能只把素材移到外部目录就称为完成。
- 噜噜和噜妹的现有动作可作为首批包的内容，不能成为新框架要求所有角色实现的标准清单。

本文优先于 `创意想法.md` 中涉及固定角色动作、固定动作按钮、统一动作集合和固定动画优先级的旧方案；其他没有冲突的桌面和联网功能继续沿用。

## 建议的代码改造范围与顺序

以下记录本次实现前的绑定及改造依据。现已增加 `packages.py`、`behavior.py`、`package_player.py`、`package_ui.py` 并迁移客户端与服务端；后续范围见使用说明。

| 现有位置 | 当前绑定 | 建议调整 |
| --- | --- | --- |
| `offwork_pet/characters.py` | `CHARACTERS` 固定角色、按名称分支绘制 | 角色目录提供清单与缩略图；渲染器接收当前包实例 |
| `offwork_pet/sprites.py` | 固定 `lulu3d` 路径、`idle/pet/drag` 等分支、64 帧缓存 | 通用帧/图集读取与时间播放；按解码字节预算缓存 |
| `offwork_pet/core.py` | 配置只接受 `lulu/lumei` | 保存稳定包标识；包是否可用交给角色目录解析，缺失包不应导致整份倒计时设置重置 |
| `offwork_pet/app.py` | 固定角色下拉项、摸头与远程动作处理、硬编码特效 | 动态角色管理、统一输入事件、运行时驱动绘制、包声明的菜单入口 |
| `offwork_pet/buddy.py`、`buddy_ui.py` | 固定互动按钮、动作合并及角色名称 | 同步能力快照、动态按钮、按能力声明发送；不能默认所有互动都支持计数合并 |
| `server/app.py`、`server/store.py` | 固定角色名与 `pinch/bonk` 白名单 | 通用包摘要和能力快照、通用互动标识校验与转发；保留现有身份、配对和限频约束 |
| `tests/`、`tools/package_release.py` | 已有角色与动作、内置素材分发约定 | 添加不同包的契约测试；应用与角色包分别出包，保留原有系统功能回归 |

代码职责建议拆为“包模型与校验、安装目录与版本管理、资源播放与缓存、事件与行为调度、系统界面与联网适配”。最终模块文件名在实现时决定，不要求一次重写全部代码。

按以下顺序推进，每一步有可见成果：

1. **先固定最小包规范**：完成格式草案、最小示例、校验器与独立预览。用两个动作名称、数量和初始状态完全不同的包验证通用性。
2. **打通本地角色运行**：将噜噜的帧资源转为标准包，支持导入、切换、删除、动态菜单和无角色空状态。噜妹的现有 Qt 绘制先导出为标准素材，再制作其包；不允许包夹带 Python 绘制代码。
3. **补齐行为交互**：区域输入、手势仲裁、动作队列、冷却、打断、恢复和按字节缓存。用连续操作、重复切换和损坏包验证生命周期。
4. **迁移双人互动协议**：双方同步动态能力，客户端与服务端一起改；对旧协议使用显式版本区分，给出升级提示，不能把新互动偷偷翻译成旧的捏脸/轻捶。
5. **降低创作门槛**：提供角色包模板、动作预览、区域编辑、规则配置与一键导出；添加外部图集转换器。
6. **最后接在线工坊**：包的浏览、下载、作者与授权展示、版本更新；下载后复用本地安装流程，不新增一套角色运行逻辑。

第 1–4 步形成“系统 + 可分享角色包”的核心闭环。在线工坊不是完成该闭环的前置条件，复杂渲染器和完整养成系统也不是第一版的必要条件。

## 后续验收方向

- 不修改主程序，导入两个动作数量、名称和初始状态均不同的包，均能正常运行。
- 增加、删除普通动作后，菜单、事件响应与状态切换随包变化，不依赖固定动作名称。
- 缺少名为 `idle`、`pet`、`receive_pinch` 等动作，仍能通过验证和正常运行，只要包内声明完整。
- 双方使用不同角色包，也能通过动态能力发现发起对方支持的互动；旧能力请求被明确处理。
- 所有角色均可删除，删除最后一个角色后可以重新导入恢复使用。
- 多次切换和删除不会持续累积旧动画、计时器和队列；大量已安装但未启用的角色不会被整套载入内存。
- 不兼容或损坏的包给出具体反馈，正常的窗口操作、倒计时和联网控制不受包影响。

验收清单用于约束后续实现；本次未执行上述验证。
